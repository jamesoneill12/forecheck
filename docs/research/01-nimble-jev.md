# Primary-source scan: Bespoke Nimble & TypeSafe Jev

Date of research: 2026-09-20. Both projects are **extremely recent** — Jev launched publicly ~2026-09-18, and Nimble was released ~2026-09-18/19 as a fast open-weight reaction to it. Treat all figures as early/unstable; several are self-reported or from a single independent blog post.

---

## 1. Bespoke Labs — "Nimble" (Bespoke-Nimble-9B)

| Field | Finding |
|---|---|
| **Name / org** | Nimble, by Bespoke Labs (bespokelabs / bespokelabsai). |
| **First release** | Repo created 2026-09-18T09:07:48Z, last push 2026-09-20T19:44:35Z (GitHub API, `https://api.github.com/repos/bespokelabsai/nimble`). Explicitly built in ~2 days as a reaction to Jev's viral launch. |
| **Last update / maintenance status** | Active as of 2026-09-20 (pushed within hours of this scan). Too new to assess long-term maintenance. |
| **What problem it solves** | "Local typed decisions" — takes text + a **flat schema** (single-choice enum, boolean, or ordered rating) and returns the picked answer plus a probability per allowed option, without generating free-text reasoning. General-purpose structured-decision/classification, explicitly **not** agent-action-specific (no built-in notion of tool calls, permissions, or trajectories). Source: README, `https://github.com/bespokelabsai/nimble`. |
| **Unit of classification** | Single (context, schema) call — one flat set of questions per invocation, scored independently/in parallel via a shared KV-cache prefill. No trajectory or multi-step-history concept in the schema. |
| **Consumes identity + permissions + org policy?** | **No.** Input is "text and a schema" only. No fields for authenticated principal, roles, agent identity, delegated permissions, or org policy in the documented schema or example data. (README / TRY_NIMBLE.md, `https://github.com/bespokelabsai/nimble/blob/main/docs/TRY_NIMBLE.md`) |
| **Model-based vs rules-based** | Model-based: LoRA adapter (rank 16) on **Qwen3.5-9B**, LR 5e-5, effective batch size 8, 1 epoch, BF16. (HF model card, `https://huggingface.co/bespokelabs/Bespoke-Nimble-9B`) |
| **Open: code?** | Code is public at `github.com/bespokelabsai/nimble`, but **GitHub's API reports `license: null`** — i.e., no machine-detected LICENSE file at repo root as of 2026-09-20 — even though the HF model card claims Apache-2.0. This is an inconsistency; **code license is NOT VERIFIED** (README shows no visible license badge either). |
| **Open: weights?** | Yes — `bespokelabs/Bespoke-Nimble-9B` on Hugging Face, model card states **Apache 2.0** license for the LoRA adapter (~165 MiB), built on Qwen3.5-9B (9B params; Qwen3.5's own license applies to the base weights and was not separately checked). |
| **Open: data?** | Yes — `data/train.jsonl` (2,676 synthetic examples across 10 domains) and `data/eval.jsonl` (324 held-out examples) are in-repo. Vendor states "all labels are synthetic: a model checked them, and no person has reviewed them." |
| **Open: training recipe?** | Yes, documented in-repo: LoRA rank 16, LR 5e-5, batch 8, 1 epoch, BF16; **"contrastive data curation"** — near-identical example pairs differing in one fact that flips the label, explicitly credited as "heavily inspired by Bespoke-MiniCheck." Authors state **"we did not distill from Jev"** — Jev was used only to score/benchmark, not to generate training labels. |
| **Probability/calibration support** | Emits a softmax probability per candidate token/answer (constrained-token logit scoring, not generation), **but the vendor explicitly disclaims calibration**: "A probability of 0.9 does not mean that the answer is right 90% of the time. Test any probability threshold on your own data before you rely on it." (README) This is a materially weaker claim than "calibrated." |
| **Sequence awareness** | None documented — flat schema per call, no history/trajectory field, max 2,048 tokens per prompt, no nesting. |
| **Latency claim + hardware** | Vendor-reported: ~106 ms median/example on H100 GPU (120-example test); ~444 ms median/example on Apple M5 Pro (324-example test), using shared-KV-prefill parallel scoring on Mac vs independent per-field scoring on GPU. (README) Not independently reproduced by us. |
| **Benchmark available** | Self-reported 90.12% match to reference labels on their own 324-example held-out set (vs. Jev 1.13.0 at 93.21%, base Qwen3.5-9B at 66.36%). Also appears as an entry in the independent **JevBench** leaderboard (`https://benchmarkheaven.com/jev-models`, MIT-licensed harness + public tasks, scored 2026-09-20 by "Benchmark Heaven," 534 decisions across easy/standard/judge/hard tiers, ranking 28 "Jev-class decision" systems on Intelligence/Calibration/Speed/Cost). We did not extract Nimble's specific JevBench rank/score. |
| **License + commercial-use constraints** | Weights: Apache-2.0 per HF card (permissive, commercial use OK) — **but base model Qwen3.5-9B's own license was not checked** and may impose its own terms. Code: license unclear/undetected (see above) — **NOT VERIFIED**, do not assume Apache-2.0 applies to the code without confirming a LICENSE file exists. Note also public friction: AI researcher Susan Zhang publicly claimed Nimble/the reaction "violated terms of use" of Jev (`https://x.com/suchenzang/status/2101196249726611620`); this concerns **using Jev's own outputs/service for benchmarking against TypeSafe's ToS**, not Nimble's own license — Bespoke's response is that Jev was only used for eval, not distillation, and Zhang herself notes such ToS terms are "most likely not enforceable." This is a vendor dispute, not a resolved legal fact — flag as reputational/legal risk context only. |
| **Overlap with our project** | Shares the "typed, per-field probability from constrained-token logits" inference technique we're considering, and the "small LoRA on an open base model" cost profile. But it is a **generic structured-decision engine**, not agent-tool-call-risk-specific: no identity/permissions/policy schema fields, no trajectory/sequence modeling, no notion of destination trust or resource sensitivity, and calibration is explicitly disclaimed rather than engineered for. |
| **Remaining gap** | Everything domain-specific to agent-tool-call risk (our 11 named dimensions, principal/role/delegated-permission modeling, trusted-vs-untrusted observation provenance, destination trust, dev/prod environment awareness, sequence-of-actions modeling, and genuine calibration guarantees) is absent and would need to be built from scratch on top of (or instead of) this pattern. |

## 2. TypeSafe AI — "Jev"

| Field | Finding |
|---|---|
| **Name / org** | Jev, by TypeSafe AI. Founder reported as Diogo Almeida, described as a former OpenAI researcher who worked on ChatGPT/RLHF (TechCrunch, `https://techcrunch.com/2026/09/18/a-new-kind-of-ai-model-from-a-chatgpt-inventor-is-thrilling-developers/`). Note on name: the user's "TypeSafe 'Jev'" was **correctly remembered** — TypeSafe AI is the real org and Jev is the real, current flagship model name (not a mis-recollection); confirmed via official docs at `https://docs.typesafe.ai/introduction` and homepage `https://typesafe.ai/`. |
| **First release** | Public launch ~2026-09-18 (TechCrunch coverage same date); homepage page metadata dated 2026-09-20, "early access" console at `console.typesafe.ai`. |
| **Last update / maintenance status** | Actively iterating within days of launch — third-party benchmark (dev.to post, dated 2026-09-17/18) tested both `jev-latest` and `jev-preview` model versions, implying rapid version churn. |
| **What problem it solves** | Vendor framing: a "System One model" — fast, structured decision-making for software, contrasted with slow/expensive "System Two" LLM reasoning. Three primitives: **Choice** (select from options), **Score** (rubric rating), **Noul** (binary truth judgment), each returned with "typed answers + probabilities + confidence." Marketed generally for automation/routing/classification, not exclusively for agent tool-call risk — but agent tool-call risk is one of its headline use cases (see below). |
| **Unit of classification** | Per official docs: "questions" evaluated "in parallel and in isolation" against a supplied "state" — i.e., single-call, flat-schema evaluation, same shape as Nimble. The independent LangChain integration (`langchain-typesafe`, `TypeSafeClassifier`) similarly passes a single state + question set per `.invoke()`. **No trajectory/sequence-of-actions concept found in any primary source.** |
| **Consumes identity + permissions + org policy?** | **NOT VERIFIED as built-in.** Official docs describe a generic "state" (text/structured data/LangChain messages) + questions; no documented first-class fields for authenticated principal, roles, delegated permissions, or org policy. The LangChain `AutoModeMiddleware` example passes tool-call context (e.g., bash commands) but the docs excerpt we fetched didn't show identity/policy fields — this may be assembled by the caller into the free-form "state" blob, which would count as "partial" (possible via prompt-shaping) rather than a modeled, typed input. |
| **Model-based vs rules-based** | Model-based. Vendor describes training via **"reinforcement learning from calibrated decisions" (RLCD)** on synthetic data (TechCrunch); architecture is a transformer but TypeSafe has **not disclosed** base model identity or parameter count — "architecture details withheld; suspected to build on an open-weight LLM foundation" (TechCrunch, unconfirmed/speculative). |
| **Open: code?** | No. API/hosted-only ("one request" architecture, requires `TYPESAFE_API_KEY`; console-based early access). No GitHub repo for the model itself found. |
| **Open: weights?** | No. Not released; proprietary. |
| **Open: data?** | No. Trained on undisclosed synthetic data; nothing published. |
| **Open: training recipe?** | No public recipe beyond the "RLCD on synthetic data" characterization from a news article (vendor claim, not a paper/technical report — **NOT VERIFIED** in detail, no arXiv paper or technical blog post located). |
| **Probability/calibration support** | Central marketing claim: "returns typed decisions with calibrated probabilities, so your software can account for uncertainty" (typesafe.ai homepage) and "every Jev decision comes with a confidence estimate" (docs). This is a **vendor claim**; independent evidence is thinner than the marketing implies (see benchmark note below). |
| **Sequence awareness** | **NOT VERIFIED / apparently absent.** No documentation found describing multi-step trajectory input, history of prior actions, or sequence-level risk (e.g., "suspicious sequence of otherwise-benign calls"). Every source describes single-state, single-call evaluation. |
| **Latency claim + hardware** | Vendor/press claims only, hosted API so no user-controlled hardware: "up to 200x faster inference and 400x lower cost than comparable LLMs" (TechCrunch); "5-18x faster than OpenAI's Luna 5.6" per a Vercel case-study cited in TechCrunch; pricing "$42 per billion input tokens," claimed "238x cheaper than Claude Fable 5.1" (typesafe.ai homepage — note: figure not independently verified, and comparison model naming should be treated cautiously). |
| **Benchmark available** | (a) Vendor/press-cited case studies (Vercel safety classification, Bryo AI email classification) — vendor claims, not independently reproduced. (b) Independent **JevBench** (`benchmarkheaven.com/jev-models`, MIT-licensed harness, scored 2026-09-20) ranks Jev alongside Nimble and ~26 other "Jev-class" systems on Intelligence/Calibration/Speed/Cost — we did not extract Jev's specific rank/score from this scan. (c) Most directly relevant to our scope: an independent developer benchmark specifically on **agent tool-call risk** — "I Benchmarked Jev on Agent Tool-Call Risk. Calibration Held." (`https://dev.to/webofmike/i-benchmarked-jev-on-agent-tool-call-risk-calibration-held-49i3`). Findings: 60 hand-labeled cases, categories **readonly / destructive / privileged / exfiltration** (a 4-way action-risk taxonomy, not our 11-dimension typed-probability scheme); 91.7% overall accuracy (55/60); 100% on "clear" cases (34/34), 71.4% on "ambiguous" (10/14), 91.7% on "adversarial" (11/12); every incorrect answer had confidence <1.0 (a weak but real calibration signal); author explicitly cautions **n=60 is too small to treat 91.7% as settled**, notes no frontier-LLM baseline was run, and that most predictions clustered in the 0.9–1.0 confidence bin (limits calibration assessment). Input to this benchmark was **command text only** (e.g., `kubectl delete namespace prod`) — no identity/permissions/trajectory/org-policy context was supplied, and evaluation was **single-call, not trajectory-aware**. |
| **License + commercial-use constraints** | Hosted SaaS; TypeSafe's Terms of Use page (`https://typesafe.ai/terms` — fetched but **confidence in exact wording is moderate**, treat as NOT FULLY VERIFIED) appears to prohibit reverse-engineering/scraping the service but does not obviously restrict how customers use model *outputs*; no evidence of an open license for weights/code since none are released. The Susan Zhang tweet (`https://x.com/suchenzang/status/2101196249726611620`) alleges Nimble's benchmarking-against-Jev "violated terms of use" — an unresolved, disputed claim about TypeSafe's ToS, not a confirmed legal finding. |
| **Overlap with our project** | Closest positioning match to our proposed project's *output shape* (typed choice/score/bool + probability + confidence) and Jev is **already being pitched and independently benchmarked for exactly our target use case** (agent tool-call risk, with a 4-category taxonomy: readonly/destructive/privileged/exfiltration). This is a real, live commercial competitor for the narrow "classify a tool call's risk" slice of our scope. |
| **Remaining gap** | No public evidence Jev models: our 11 named typed dimensions (in particular prompt_injection_influence, unauthorized_scope, policy_conflict, suspicious_action_sequence — this last one requires trajectory modeling Jev doesn't appear to have); ingestion of authenticated principal/roles/delegated agent permissions/org policy as structured, typed inputs (vs. free-text "state"); trusted-vs-untrusted observation provenance tagging; destination-trust or resource-sensitivity typed fields; dev/prod environment conditioning; or a separate deterministic policy engine downstream (Jev appears to conflate "decision" and "confidence" without a documented separate ALLOW/REVIEW/DENY policy layer). It is also **closed** end-to-end (no code/weights/data/recipe), unlike our vendor-neutral open-source goal. |

## Architectural lessons for us

**What to copy:**
- The **constrained-token / candidate-logit scoring** approach (Nimble's documented mechanism, and almost certainly Jev's too, given the "no free-text generation, pick from typed choices" framing) is a good match for cheap, low-latency, typed multi-dimension output — it avoids parsing free-form JSON and gives a natural per-field probability via softmax over a small candidate set.
- **Shared KV-prefill across multiple questions against one context** (Nimble's approach; encode the shared context/schema once, score N fields off the same prefix) is directly applicable to our 11-dimension output: encode (objective, identity, trajectory, action, org policy, environment) once, then score all 11 typed probabilities off the same prefill instead of 11 separate forward passes.
- **Contrastive synthetic data curation** (near-identical example pairs that differ in one decision-relevant fact) is a promising, cheap way to generate hard negatives for each of our 11 dimensions (e.g., same tool call, but principal has vs. lacks the role that authorizes it).
- Both projects show a small LoRA-on-open-base-model is viable for this task class — supports our "vendor-neutral, can run on commodity open models" design goal.

**What we must not assume:**
- Neither project's probabilities should be assumed calibrated out of the box. Nimble's own vendor explicitly disclaims calibration ("test thresholds yourself"); Jev's calibration claim is marketing-forward and the one independent test we found (n=60) is far too small to validate it, and confirms only a weak signal ("wrong answers never hit 1.0 confidence"), not properly calibrated probabilities (e.g., no reliability diagram, no ECE reported anywhere). **Do not inherit "confidence" as a proxy for "calibrated probability" without our own calibration evaluation** (e.g., ECE/Brier score against held-out labeled data), which is a stated design goal of our project and a real differentiator if we get it right.
- Neither system is trajectory/sequence-aware in any verified way — this directly matches our `suspicious_action_sequence` dimension being a genuine gap, not something we can borrow. We will need to design sequence modeling (e.g., trajectory encoding, not just flat single-call state) ourselves; don't assume prior art solved it.
- Neither system has verified, structured ingestion of identity/roles/delegated-permissions/org-policy as typed fields (both appear to rely on flattening everything into a free-text "state" or "context" blob). If true, this is a real architectural gap we can differentiate on, but we should not assume either vendor has quietly solved this just because their docs are thin — flag as unverified rather than assumed absent for Jev specifically, since TypeSafe's docs excerpt was incomplete.

**License constraints:**
- Nimble's **weights** are Apache-2.0 (reusable), but its **code license is unverified** (GitHub API shows no detected LICENSE file) and its base model Qwen3.5-9B's own license terms were not checked — confirm both before reusing any Nimble code or redistributing a Qwen3.5-9B-based derivative.
- Jev is fully closed (no code/weights/data) — nothing to reuse under any license; any comparison/benchmarking against the live Jev API should be done carefully given the disputed ToS allegation (Susan Zhang tweet) about benchmarking-derived "violations," even though that claim is unresolved and disputed as unenforceable.
